## 日常部署

### 方式一：GitHub Actions（推荐）

推送到 `main` 分支即自动构建并部署：

```bash
git add -A && git commit -m "..." && git push
```

首次使用前需在仓库配置两个 Secret（已配置）：

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`

### 方式二：本地手动部署

```bash
npm run cf:build      # 产出 .open-next/worker.js
npm run cf:deploy     # 构建 + 部署
```

本地部署需带上凭据：

```bash
export CLOUDFLARE_API_TOKEN=...
export CLOUDFLARE_ACCOUNT_ID=...
```

## 数据运维脚本

```bash
# 把本地 .data/db.json 全量写进 KV（首次上线或重置数据）
CLOUDFLARE_ACCOUNT_ID=xxx CLOUDFLARE_API_TOKEN=yyy node scripts/seed-kv.mjs

# 确保管理员用户存在于 KV（首次登录就不用现场创建，快得多）
CLOUDFLARE_ACCOUNT_ID=xxx CLOUDFLARE_API_TOKEN=yyy ADMIN_USER=superjohnson node scripts/ensure-admin.mjs

# 导出线上整库做备份（做任何破坏性操作前先跑一遍）
CLOUDFLARE_ACCOUNT_ID=xxx CLOUDFLARE_API_TOKEN=yyy node scripts/backup-kv.mjs

# 整库「瘦身」：体检（不写入）
CLOUDFLARE_ACCOUNT_ID=xxx CLOUDFLARE_API_TOKEN=yyy node scripts/slim-kv.mjs
# 确认报告无误后真正写回（写回前会自动备份到 .data/backup/）
CLOUDFLARE_ACCOUNT_ID=xxx CLOUDFLARE_API_TOKEN=yyy node scripts/slim-kv.mjs --apply
```

`slim-kv.mjs` 也可以在 GitHub Actions 里跑，无需本地配令牌：
**Actions → KV Maintenance (slim) → Run workflow**（`apply` 不勾选即体检模式）。
站点已经进入 1102 状态时**只能走这条路径** —— 理由见下面「常见问题」。

## 已知局限与后续建议

1. **整库单键覆盖写**：所有集合存在同一个 KV 键 `db:v2` 上，每次写都是整库覆盖。多用户并发写会互相覆盖丢数据。当前只适合单人多设备使用。
   - ⚠️ **连带的体积预算问题（真实事故）**：单键存储意味着**每个请求都要把整个库 JSON.parse 一遍**，这份开销算在 Worker 的 CPU 预算里。实测把 414 个 OKX 带单员的原始字段全量落盘后，这个键涨到约 1.8 MB，全站读库路径立刻开始返回 `error code: 1102`（503）。
   - 所以**新增落盘字段前先问一句「列表真的会渲染它吗」**。已落盘的字段体积账见 `lib/okx-copy.ts` 里 `rankToTrader` 上方的备忘，以及 `lib/store.ts` 中关于体积预算的注释。
   - 生产化建议：换成 **Cloudflare D1**（SQLite，免费额度 5GB / 500 万行读每天），只改 `lib/store.ts` 一个文件，业务代码无需改动。
2. **KV 最终一致**：写入后全局传播最长约 60 秒。刚登录后立刻大量并发请求，可能出现部分页面鉴权失败，稍后自动恢复，属正常现象。
3. **验证码为演示实现**：固定演示码 `888888`，未接真实邮件服务。接真实邮件需配置邮件服务商 API（Resend / 阿里云邮件推送等）。
4. **首次写入较慢**：边缘环境下每次落盘都是一次网络往返，因此所有批量写入都做了合并（`insertMany`、seed 的内存缓冲）。新增写逻辑时请沿用这一模式。

## 常见问题

**构建报 `No open-next.config.ts file was found`**
→ 项目根目录缺 `open-next.config.ts`。

**构建报 `Not enough non-option arguments`**
→ OpenNext CLI 需要显式子命令：`opennextjs-cloudflare build`，不能只写 `opennextjs-cloudflare`。

**npm install 报 `Unexpected end of input` / 解包损坏**
→ Windows 下安装被中断会留下截断文件。删掉 `node_modules` 重装，并加 `--ignore-scripts` 规避 esbuild 的文件锁。

**访问自定义域名返回旧的页面**
→ 若本地跑过 `next start`，可能仍占着端口；确认部署版本号已更新（`wrangler deploy` 输出中的 Version ID）。

**全站 503，响应体是 `error code: 1102`**
→ Worker CPU 时间超限，不是权限/路由问题。判断特征：`/login` 正常 200，而**所有要读库的路径**（含 `/api/market` 这种不关心 traders 的接口）一起 503。
→ 根因几乎一定是 KV 里的 `db:v2` 太大了（单键存储，每个请求都要整库解析）。先跑 `slim-kv.mjs` 体检看体积，再 `--apply` 写回；也可以走 Actions 的 **KV Maintenance (slim)**。
→ ⚠️ 这时**不要**指望应用内的接口自救：`POST /api/okx/traders {mode:"compact"}` 本身也要读库，一样跑不起来。必须绕开 Worker 直连 KV。
